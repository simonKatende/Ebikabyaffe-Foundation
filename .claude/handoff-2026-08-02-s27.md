## Backend phase 1 — real member accounts + lineage verification (`65cb125`)

Account creation, sign-in, sign-out, session persistence, and "Get verified by Omutaka" submissions now hit the real Supabase project instead of resetting on reload.

- **Session minting**: a new `POST /api/auth/phone-session` route (service role) mints a real session for a deterministic synthetic email (`<e164>@members.ebikabyaffe.internal`) via `admin.generateLink` + `verifyOtp`, redeeming it server-side so nothing is ever actually emailed/texted — the on-screen demo OTP in `LoginFlow.tsx` is unchanged, it's what gates entry into this route.
- **Real bug found**: `generateLink({type:"magiclink"})` actually issues a **"signup"**-typed link the first time it creates a brand-new user (only a genuine `"magiclink"` link on later calls) — `verifyOtp` must be called with the link's own `verification_type` field, not a hardcoded `"magiclink"`, or first-time account creation fails with a cryptic `otp_expired` error.
- **`AuthContext.tsx`** rewritten: bootstrap is a single `onAuthStateChange` subscription (no separate `getSession()` call — this repo's `react-hooks/set-state-in-effect` lint rule rejects that shape), `updateUser()` writes through to `profiles`/`lineages` optimistically-then-in-background. `lib/auth/registry.ts` (the old session-only phone→name map) is deleted, replaced by a new `GET /api/auth/check-phone` route.
- New shared **`lib/phoneCountries.ts`** (country/dial-code table + E.164↔display formatting) so `LoginFlow.tsx` and `AuthContext.tsx` don't duplicate it.
- `ProfileContent.tsx`'s phone field is now locked/display-only — phone is the fixed real-account identity.
- New migration `20260802120000_avatar_column.sql` (adds `profiles.avatar_data_url`, a field that postdates the original s19/s20 schema).

## Backend phase 2 — Bataka Panel, business listings, announcements (`4863035`)

Prompted by the user asking for advice on the panel's access model given the real shape: **one Foundation admin, up to 56 clan Bataka offices**. Resolution: keep per-clan-office credentials (the existing 56 distinct clan passwords + 1 admin password in `lib/batakaPanel/passwords.ts` — not one shared secret, not real named-individual accounts) but fix the actual vulnerability — those passwords lived in the client JS bundle and `panelSignIn()` was an unauthenticated client-side state flip anyone could fake from devtools.

- **One real Supabase Auth account per clan OFFICE** (57 total), lazily provisioned on first successful login via new `POST /api/batakaPanel/session` — `passwords.ts` is now imported only by that server route (confirmed absent from the built client bundle via grep).
- **`lib/supabase/mintSession.ts`** — the generateLink/verifyOtp logic extracted out of phase 1's route so both routes share one tested implementation.
- **`lib/supabase/panelClient.ts`** — a SECOND Supabase browser client with a distinct cookie namespace (`sb-panel-auth`), so a signed-in member and a signed-in officer/admin coexist in the same browser. Real gotcha documented in the file: `@supabase/ssr`'s `createBrowserClient` caches ONE instance in a module-level variable shared across the whole app by default — a second call with different `cookieOptions` would silently just return the first (member) client unless `isSingleton: false` is passed.
- **`lib/batakaPanel/store.ts`** and **`lib/businesses/store.ts`** reimplemented against real tables, public API unchanged (confirmed via grep all 15 consuming files only ever call the exported functions). Officer decisions (verify/decline/request-info) go through new `panel_verify_member`/`panel_decline_member`/`panel_request_info` **SECURITY DEFINER** SQL functions instead of a raw RLS UPDATE policy, so an officer's write access is scoped to exactly the review columns.
- **Realtime (Postgres Changes, RLS-scoped) replaces `crossTabSync` for these two stores** — verified live: one officer tab verifies a member, a second tab (same browser, no reload) sees the status flip in place.
- **Real pre-existing RLS bug found and fixed**: `lineages_select_by_clan_officer` was scoped to the lineage's own *declared* `father_clan_slug` instead of the member's actual joined clan (`profiles.clan_slug`) — the one case they'd legitimately differ is exactly the fraud/error case the panel's own "automatic checks" UI exists to catch, so the old policy hid it from the right officer and showed it to the wrong one.
- **Real session-identity bug found**: `mintSession()` was reusing one service-role client for both the auth-mint call and subsequent privileged writes — `verifyOtp` silently switches that same client's identity to the newly-authenticated user, so `panel_officers` inserts were running as the brand-new officer (no self-insert policy) instead of service role. Fixed by giving `mintSession` its own disposable client.
- New migration `20260802130000_panel_phase2.sql`: `announcements.posted_by_admin` column (missing since s19 predates that s26 feature), a full `business_listings` table (didn't exist at all — built as a frontend mock in s24, after the s19 backend scaffold), and `is_panel_admin()` helper (business-listing *decisions* are admin-only while officers keep view-only, so a single `is_clan_officer()` check can't express it).
- Deleted `lib/batakaPanel/mockMembers.ts`, `mockAnnouncements.ts`, `lib/businesses/mockBusinesses.ts` — confirmed via grep they had no other importers.
- Verified end-to-end via Playwright: real per-clan-office sign-in → member verify with a real audit trail → admin-only business-listing decisions (officer sees, can't decide; admin decides) → admin post-on-behalf-of-clan announcement with correct Foundation attribution → clan-scoping isolation (a Mmamba officer cannot see Lugave's data).

## Backend phase 3 — real member counters + real photo storage (`7f9ce12`)

Two parts, same commit, both preceded by a direct question to the user since they touch public-facing content: the site-wide "Baganda registered"/"Verified by Bataka" figures and most per-clan counts were **never real** — they were the original marketing placeholder numbers (847,213 / 12,847 / large per-clan estimates) baked in before any backend existed. User confirmed: go real everywhere, site-wide AND per-clan, even though the real number is currently small.

- Two new `SECURITY DEFINER` SQL functions, explicitly `grant execute`'d to `anon` (existing functions like `is_clan_officer()` never needed this since they were only ever called internally/by an authenticated client): `public_site_stats()` and `public_clan_member_counts()` — aggregate counts only, never row data, so no visitor gains new visibility into individual `profiles` rows.
- `lib/stats.ts` keeps its exact public API (11 consuming files unchanged); the existing optimistic per-action delta (`recordRegistration` etc.) stays for instant feedback, now layered on a real fetched baseline. `clanMemberCount` is now always non-null — the "Member count coming soon" fallback and the now-fully-unused hardcoded `memberCount` field on 11/56 clans in `lib/clans.ts` were removed.
- **`lib/crossTabSync.ts` is fully deleted** — `lib/stats.ts` was its last remaining user after phase 2 retired the panel/business stores off it (confirmed via grep before deleting).
- **Photos**: new public Storage bucket `member-media`, owner-scoped write RLS via `storage.foldername(name)[2] = auth.uid()`. Path convention is deliberately extension-less (`avatars/{id}/photo`, `businesses/{id}/photo`, `contentType` set explicitly on upload) so a re-upload in a different format always overwrites the same object instead of orphaning the old one. `lib/photoUpload.ts`'s `readPhotoAsDataUrl` became `uploadPhoto(file, path)` — same upfront format/size validation, now uploads to Storage and returns the public URL.
- **Field/column names (`avatarDataUrl`, `photo_data_url`) were deliberately NOT renamed** even though they now hold a real URL instead of a base64 string — flagged as a possible cosmetic follow-up, not done, to keep this pass small.
- New migrations `20260803120000_public_stats.sql` and `20260803130000_photo_storage.sql`.
- Verified end-to-end: a fresh, unrelated browser context saw the exact same real count a just-created account had bumped (proving DB-backed, not local state); a real photo upload landed in Storage and rendered from its public URL; a cross-account write attempt to another member's photo path was rejected by RLS.

## Real RSVP/event-signup tracking (`c7dc670`)

User asked "what else needs to be updated to the database?" — the RSVP/Empango buttons still didn't persist anything real even after the email-nudge fix above, just a smarter toast. Built real tracking:

- New `event_rsvps` table — ONE shared table for both the Parliament-meeting RSVP and the Empango-updates signup (structurally identical: "member consents to be notified about event X"), distinguished by an `event_key` slug (`"parliament-land-law-2026-05-15"`, `"empango-2026"`). Events themselves are still hardcoded content in the React components, not database rows.
- Email is **snapshotted at RSVP time** (not live-joined to `profiles.email`) — it's specifically the address the member consented to be contacted at for that event, shouldn't silently change if they later edit their profile.
- RLS: owner select/insert own rows; `is_panel_admin()` can read all of them (no panel UI built for this yet, but the data's there for a future one without a schema change).
- New `lib/eventRsvps.ts` (`hasRsvped`, `recordRsvp`). Both buttons now check on mount whether the member already has a row for that event and show a disabled "✓ already done" state instead of being repeatably clickable.
- New migration `20260803140000_event_rsvps.sql`.
- Verified: RSVP records even with no email set (still nudges to add one), both buttons' "done" state survives a hard reload (proving DB-backed), real rows confirmed via direct query, cascade-deleted cleanly with the test account.
