## The bug

`AuthContext.tsx`'s `loginWithPhone` rebuilt the signed-in `user` object from `DEFAULT_USER` on **every** sign-in, not just account creation. Sign-in mode (`LoginFlow.tsx`, `mode==="signin"`) calls it with no `clanSlug`, so every sign-out → sign-in cycle wiped the member back to blank defaults — clan, email, avatar, Sacco status, verification, lineage, business listing — and even reset `clanSlug` itself to `null`, which directly contradicts s24's "every account's clan is permanently locked" rule. This wasn't a reload-related mock limitation (the documented "resets on hard reload" behavior everywhere else in this app) — it was happening on plain in-session sign-out/sign-in, no reload involved, which is why it read as a genuine regression to the user rather than an accepted mock gap.

## The fix

Added a session-only, phone-keyed profile snapshot store inside `web/context/AuthContext.tsx` (module-level `Map<string, AppUser>`, same pattern already used by `lib/auth/registry.ts` and `lib/batakaPanel/store.ts` — resets on hard reload like the rest of the app's mocks, replaced by the real backend user row in Phase 2):

- `updateUser(patch)` now writes the resulting merged user into `profilesByPhone` keyed by `next.phone`, in addition to updating React state — every edit anywhere in the app (avatar upload, Sacco donation flag, lineage submission, business listing, etc.) is captured automatically since they all funnel through `updateUser`.
- `loginWithPhone({name, phone, clanSlug})`: if `clanSlug` is `null`/absent (sign-in path) **and** a snapshot exists for that phone, restores it (with the freshly-typed `name`/`phone` applied) instead of rebuilding from `DEFAULT_USER`. Account creation (`clanSlug` provided) still always starts a brand-new profile, as intended for a genuinely new member — and immediately seeds `profilesByPhone` with it, so a same-session sign-out/sign-in on that same phone will now correctly round-trip.
- No other files needed to change — `LoginFlow.tsx`'s call sites were already correct (sign-in passes no `clanSlug`, create passes one); the bug was entirely inside `AuthContext.tsx`'s own reset logic.

Verified via `tsc --noEmit` and `eslint` on the changed file (both clean) plus a full `npm run build` (75 pages, clean) before committing — no interactive/browser verification was run this session (short, targeted fix, not a UI change).
