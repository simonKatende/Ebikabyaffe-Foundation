# Session 28 handoff (2026-08-02)

New conversation, same day as s27. Three real pieces of work, all Playwright-verified against the live Supabase project with test data cleaned up afterward:

**1. Fixed a real session-isolation bug in the Bataka Panel / Foundation Admin split (s26).** The user reported that signing into `/batakaPanel` as a clan officer, then opening `/foundationAdmin` in a new tab, skipped straight to the shared dashboard instead of asking for the admin password — and vice versa. Root cause: both doors shared one Supabase cookie (`sb-panel-auth`), so either login satisfied both gates. Fixed by splitting `lib/supabase/panelClient.ts` into two fully independent clients/cookies (`sb-panel-officer-auth` / `sb-panel-admin-auth`), and reworking `lib/batakaPanel/store.ts` to track both auth states with a **per-tab "sticky" role** — once a tab is showing a role, it keeps showing it regardless of what the *other* role's cookie does elsewhere in the same browser. This surfaced two follow-on bugs, both fixed and re-verified: (a) the sticky rule could silently block an admin's own sign-in from ever taking effect, if that same tab had passively discovered an unrelated officer cookie on mount — fixed with a new `completeSignIn(role)` that explicitly pins the tab to the role just authenticated, rather than trusting reactive listener ordering; (b) exiting the admin session raced its own sign-out event against `FoundationAdminGate`'s redirect check and could bounce straight back into the panel — fixed by awaiting `panelSignOut()` before navigating. `lib/businesses/store.ts` also switched from the removed `createPanelClient()` to a new exported `getActivePanelClient()` (from `lib/batakaPanel/store.ts`) so its own officer/admin queries route through whichever client is actually signed in.

**2. Real contact-message replies — prompted by the user asking if a reply to "send this to the Foundation" could trigger an in-app notification**, since an email reply typed in the Foundation's personal Gmail inbox is completely invisible to the app. New `contact_messages` table (migration `20260803150000`): every submission through `ContactFoundationCard` (home dashboard) or `LineageArchiveCard` (/profile) still emails the Foundation as before via `app/api/contact/route.ts`, but now ALSO becomes a durable row — the API route requires a real signed-in session (`getUser()`, not `getSession()` — this is a server-side authenticity check, not a client bootstrap) and inserts under that member's own `profile_id`. If the email step ever fails (missing key, Resend hiccup), the message is still durably saved and the member still sees "sent successfully" — the DB row is now the source of truth, email is just a courtesy heads-up. New admin-only **Messages** tab in the Bataka Panel (`app/batakaPanel/messages` + `[id]`, `lib/contactMessages/`) — a clan officer has no legitimate reason to read a general question to the Foundation, so this tab/dashboard-queue-card only render for `isAdmin`. Replies go through a `SECURITY DEFINER` RPC (`panel_reply_to_message`), same column-restricted-write pattern as `panel_verify_member` — a member can't fake their own "Foundation reply" via a crafted raw insert. Member side: `ContactFoundationCard` now shows a red "N new replies" badge and a "Your messages" history list; expanding a replied message calls `mark_reply_seen()` (another `SECURITY DEFINER` RPC) to clear it.

**3. Blue verified badge, wherever a verified member's name appears** — modeled on Instagram/Twitter/TikTok's blue checkmark (`components/ui/VerifiedBadge.tsx`).
